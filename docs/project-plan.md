# PicForge 项目方案

> 简单、高效的在线图片工具箱。
>
> 日期：2026-11-05。本文保留最初的项目设计；V1.0–V2.0 已实现，当前交付状态见 [实现进度](implementation.md) 和 [验收记录](verification.md)。细化方案见 [水印设计](watermark-design.md) 与 [V1.2–V2.0 设计](processing-design.md)。后文的初始交付、时间估算与待办属于历史方案，不代表当前实现状态。

## 1. 项目定位与总体决策

PicForge 面向需要快速拼图、加水印、调整图片和转换格式的普通用户。核心体验是：选择本地图片，调整参数，预览结果，下载文件。

采用 **React + TypeScript + Vite 的纯前端应用**，图片计算在浏览器内完成，部署产物是静态文件。V1.0 先完成图片拼接闭环，再按版本增加工具，共用图片导入、渲染、编码和下载能力。

本方案基于以下假设：

- 优先服务中文用户，兼顾桌面和手机浏览器。
- 首版无需账户、图片上传接口、服务端处理、数据库和云端项目保存。
- 首版支持当前主流浏览器；具体支持版本随首次验收记录固定。
- 图片默认仅用于当前页面会话，刷新后需要重新选择；轻量偏好可以本地保存。
- 首版追求可靠的常用操作，不承担专业排版、印刷色彩或任意大小图片处理。

初次编写方案时，工作区尚无项目源码、依赖清单或现有设计文档，选择从单应用结构开始。此后实现已落地，当前状态以上方进度与验收记录为准。

## 2. 版本范围与交付边界

| 版本          | 用户获得的能力               | 关键交付                                                  | 完成标准                                                     |
| ------------- | ---------------------------- | --------------------------------------------------------- | ------------------------------------------------------------ |
| V1.0 图片拼接 | 横向、纵向、宫格、自定义间距 | 多图导入、排序、背景与留白、预览、PNG/JPEG 下载           | 三种布局在目标浏览器完成真实导入和导出，超限及失败可恢复     |
| V1.1 图片水印 | 文字水印、图片水印、批量水印 | 位置、大小、透明度、旋转、平铺；同一配置应用于多图        | 中文字体加载正确，预览和输出位置一致，单图失败不阻断其余任务 |
| V1.2 图片处理 | 裁剪、缩放、旋转、压缩       | 固定比例/自由裁剪、等比缩放、90°旋转与翻转、JPEG 质量调节 | 尺寸与方向正确，展示实际输出体积及变化，参数调整可恢复       |
| V1.3 格式转换 | PNG、JPEG、WebP、AVIF 转换   | 独立转换页面、格式能力检测、按需加载编码器                | 每种开放格式验证实际编码、重新解码、透明度和文件类型         |
| V2.0 批量工具 | 批量处理、ZIP 下载、预设模板 | 多步骤处理队列、取消/重试、结果清单、命名规则、模板保存   | 部分失败保留成功结果，大任务受内存预算约束，模板可迁移       |

范围衔接规则：

- V1.0 的 PNG/JPEG 是拼接结果的保存方式；V1.3 才提供独立格式转换工作流及更完整的格式选择。
- V1.1 的批量水印是“同一水印配置处理多张图”，先提供结果列表和逐项下载。V2.0 扩展为可组合的批量流程，并加入 ZIP 下载。
- V1.2 的基础压缩包括 JPEG 有损质量调整和降低像素尺寸。PNG 不提供伪造的质量滑块；保持尺寸的 PNG 无损优化另行评估编码器。
- V1.0 的宫格是规则行列布局。自由拖动图层、任意坐标拼贴、多页海报属于后续独立范围。

## 3. V1.0 功能规格

### 3.1 导入与图片列表

- 支持文件选择、多文件拖入，接受静态 JPEG、PNG、WebP；PNG/WebP 的动画变体需识别并提示不支持，避免静默丢失动画。
- 粘贴导入作为增强能力：浏览器提供图片文件时支持，不影响文件选择主流程。
- 首版对 GIF、SVG、HEIC、AVIF 等未开放输入显示明确提示；AVIF 输入随 V1.3 一起评估。
- 校验文件大小、实际格式、像素尺寸和解码结果，不只检查扩展名或 `File.type`。
- 支持拖拽排序、上移/下移按钮、移除单张、清空列表；清空需确认或提供明确撤销入口。
- 每张图展示缩略图、文件名、尺寸和处理状态，错误定位到具体图片，保留其他有效图片。
- 按用户选择顺序生成稳定 ID；异步解码完成顺序不能改变排列顺序。

### 3.2 三种拼接模式

| 模式 | 尺寸规则                                 | 可调整内容                                     |
| ---- | ---------------------------------------- | ---------------------------------------------- |
| 横向 | 所有图片按同一内容高度等比缩放，宽度累加 | 内容高度、间距、外边距、背景                   |
| 纵向 | 所有图片按同一内容宽度等比缩放，高度累加 | 内容宽度、间距、外边距、背景                   |
| 宫格 | 固定列数和单元格尺寸，按行排列           | 列数、单元格宽高、适应方式、间距、外边距、背景 |

宫格默认使用“完整显示”，保持比例并留白；用户可选择“填满裁切”，按中心裁切并在预览中显示实际结果。末行不足时保留空格，使整张图维持规则矩形。

建议默认使用纵向模式、内容宽度 1200px、间距 16px、外边距 16px、白色背景；这些是交互起点，允许调整。图片被放大时提示可能变模糊，不在背后修改用户指定尺寸。

布局计算采用独立纯函数。设图片数量为 `n`、间距为 `g`、四边外边距为 `p`：

- 横向：`W = Σ缩放后图片宽度 + (n - 1) × g + 2p`；`H = 内容高度 + 2p`。
- 纵向：`W = 内容宽度 + 2p`；`H = Σ缩放后图片高度 + (n - 1) × g + 2p`。
- 宫格：有效列数 `c = min(设置列数, n)`，行数 `r = ceil(n / c)`；`W = c × 单元格宽度 + (c - 1) × g + 2p`；高度按行数同理。

空列表不生成布局；尺寸、间距、列数校验为允许范围内的整数。先确定各图片的整数目标矩形，再累加边界，避免逐段取整形成缝隙。

### 3.3 预览与导出

- 中央展示拼接预览，支持适应窗口和缩放查看；同时显示输出像素尺寸。
- 背景可选纯色或透明，透明状态显示棋盘格；棋盘格不写入导出图片。
- PNG 保留透明通道；JPEG 输出前填充明确的背景色，默认白色。
- 提供 PNG/JPEG 选择、JPEG 质量和文件名；文件名后缀由实际编码格式决定。
- 输出按所选尺寸从原始图片重新绘制，不能直接放大缩略预览作为结果。
- 导出期间显示真实阶段，例如“正在绘制 3/8”“正在编码”。无法获得编码百分比时显示不定进度。
- 用户可以取消等待、修改后重新导出；失败时保留列表和参数，提供重试或降低尺寸操作。
- 下载成功提示使用“已生成文件并发起下载”，不把浏览器是否保存到磁盘视为已知状态。

## 4. 页面与交互设计

首版直接进入拼接工作台，减少工具首页到实际操作的跳转。V1.1 起再逐步扩展工具导航和独立页面。

| 区域       | 内容与职责                                          |
| ---------- | --------------------------------------------------- |
| 顶部       | PicForge 标识、工具导航、简短的“图片在本机处理”说明 |
| 左侧素材区 | 添加图片、缩略图列表、排序、移除、数量              |
| 中央预览区 | 空状态导入入口、拼接结果、缩放与尺寸、过程提示      |
| 右侧参数区 | 布局、尺寸、间距、外边距、背景、输出格式            |
| 导出区域   | 当前输出尺寸、生成状态、下载按钮                    |

响应式方案：

- 桌面宽度约 1200px 以上采用三栏，中央区域弹性伸缩。
- 中等宽度收起素材区或参数区，确保预览仍有足够空间。
- 手机采用纵向单列，素材和参数可折叠，底部导出入口处理安全区和键盘遮挡。
- 以 360px、768px、1440px 视口验收，不依赖固定桌面宽度。

视觉方向：浅灰工作区、白色参数面板、单一蓝紫强调色、清晰的输入控件和轻量图标。使用统一的间距、字号、圆角与颜色变量；深色主题作为后续增强。

无障碍与反馈：

- 文件选择、排序、移除、参数调整和导出都可通过键盘完成。
- Canvas 之外提供语义化图片列表、输出尺寸和处理状态；不能让读屏用户依靠画面理解内容。
- 输入控件有明确标签和错误说明；状态通过文本表达，不能只依赖颜色。
- 移动端拖动使用专用手柄，保留上下移动按钮，减少与页面滚动冲突。

## 5. 技术选型

| 层次       | 建议选择                                     | 原因                                                 |
| ---------- | -------------------------------------------- | ---------------------------------------------------- |
| 界面       | React + TypeScript                           | 组件化界面、明确的参数及任务类型                     |
| 构建       | Vite                                         | 支持 React/TS 模板，构建静态资源                     |
| 样式       | CSS Modules + CSS 变量                       | 首版界面规模可控，统一设计变量，避免整套后台组件体系 |
| 状态       | React reducer + 分域 Context                 | 集中管理编辑动作，分离参数、素材引用与任务状态       |
| 图片处理   | Canvas 2D + 浏览器解码 API                   | 覆盖拼接、裁切、缩放、旋转和基本导出                 |
| 任务执行   | Web Worker + OffscreenCanvas，保留主线程降级 | 优先把较重绘制移出界面线程                           |
| 文件对象   | File / Blob / Object URL                     | 原始文件按引用管理，避免把大图片存成字符串           |
| 单元测试   | Vitest                                       | 测试布局、参数校验、状态转换等纯逻辑                 |
| 浏览器测试 | Playwright                                   | 验证真实导入、预览、导出及异常流程                   |
| 包管理     | pnpm + 锁文件                                | 固定可复现的依赖组合                                 |

Vite 提供 React/TypeScript 模板及静态构建能力，初始化时选择相互兼容的稳定版本，固定 Node、包管理器及依赖版本；不在方案阶段盲目指定所有包使用各自最新版。[Vite 官方指南](https://vite.dev/guide/)

Reducer 与 Context 可以组合管理复杂页面，具体实现按更新频率拆分状态，避免渲染进度让全部表单重复更新。[React 状态管理说明](https://react.dev/learn/scaling-up-with-reducer-and-context)

排序交互是否引入专用库在原型阶段确定，以触屏、键盘、包体和维护情况为依据。独立路由随第二个工具加入；ZIP 库及 WASM 编码器按对应版本引入，采用功能级动态加载。

## 6. 图片处理架构

### 6.1 数据流与职责

处理链路：**本地文件 → 校验与方向归一化 → 素材记录 → 布局计算 → 缩略预览 → 按目标尺寸重绘 → 编码 Blob → 本地下载**。

拆分四类数据：

| 模型           | 保存内容                                        | 生命周期                           |
| -------------- | ----------------------------------------------- | ---------------------------------- |
| ImageAsset     | 稳定 ID、原始 File、归一化宽高、缩略图引用      | 当前会话，由素材仓库统一释放       |
| StitchDocument | 素材顺序、布局参数、背景、导出设置、修订号      | 可序列化的编辑状态，不包含像素副本 |
| RenderPlan     | 输出尺寸、每张图的源裁切区和目标矩形            | 由布局计算生成，预览与导出共用     |
| ProcessingJob  | 任务 ID、文档修订号、阶段、取消状态、结果或错误 | 每次预览/导出独立创建              |

设计约束：

- UI 负责参数与反馈；布局函数负责几何；渲染模块负责像素；编码模块负责格式；下载模块负责浏览器下载行为。
- 原始 File 保持不变；缩略图与解码位图属于可释放缓存，不写入 reducer 历史。
- 预览与导出复用同一 RenderPlan，以同一坐标系统按比例绘制，避免两个实现产生位置偏差。
- 预览缓存限制尺寸，导出时顺序解码所需原图，绘制后尽快释放。
- 快速调整参数只保留最新预览任务；旧任务按修订号丢弃结果，不能覆盖新状态。
- 导出使用点击时的参数快照；导出过程中继续编辑不改变已经开始的任务。

### 6.2 Worker 与降级

优先在 Worker 内完成解码、OffscreenCanvas 绘制和编码。OffscreenCanvas 支持在 Worker 中运行，但具体能力仍需检测。[MDN OffscreenCanvas](https://developer.mozilla.org/en-US/docs/Web/API/OffscreenCanvas)

初始化时检测 Worker、Worker 内解码、2D context、编码能力，并跑一次小图往返验证。不可用时退回主线程 Canvas，以较低并发、分段调度和较小任务预算处理。

降级路径不承诺重编码期间始终流畅，也不承诺立即停止不可中断的浏览器调用。取消后立即让任务失效、停止后续步骤；Worker 可终止并重建，主线程编码完成后的过期结果须释放。不要自动上传服务器兜底。

### 6.3 资源释放与内存预算

压缩文件大小不能代表解码成本。以 8 位 RGBA 的单份像素缓冲估算：

`像素内存 ≈ 宽 × 高 × 4 字节`

例如 12000 × 12000 的画布单份缓冲约 549 MiB，尚未包含原图、预览、编码缓冲和浏览器额外开销。这是容量估算，不是实测内存。

建议的首轮验证策略：

- 会话图片数上限先设为 20 张、单文件大小上限先设为 20 MiB，作为产品保护值；还必须检查源图像素数，不能据此承诺所有文件可处理。
- 原型阶段补齐格式头部尺寸检查，在大图完整解码前进行预判；无法可靠识别尺寸的输入应明确拒绝或进入更严格的路径。
- 导入和导出默认一次处理一张大图；不能同时解码整组照片。
- 根据“当前源图解码 + 输出画布 + 缩略缓存 + 编码余量”估算峰值，源图像素、输出面积和单边长度分别设置预算。
- 预算值由桌面及移动设备验证后确定，并记录设备、浏览器和样本；不能将某个画布尺寸宣称为全浏览器安全上限。
- 超限先提示减少图片或降低输出尺寸；仅降低输出尺寸无法解决源文件本身无法解码的问题，此时提示预先缩小原图。
- 及时关闭 ImageBitmap、撤销不再使用的 Object URL、释放旧画布和结果 Blob 引用；下载 URL 保留至不再需要，避免过早撤销。

Canvas 的尺寸和面积上限取决于浏览器与环境，超限可能使绘制失效。首版不承诺无限长图；分块绘制也不能突破最终单张 Canvas 的上限。[MDN Canvas 使用说明](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/canvas#maximum_canvas_size)

### 6.4 格式、方向与画质

- 分开记录“能否解码”和“能否编码”，不能用图片可显示推断该格式可导出。
- 编码探测需检查 Blob 的实际 MIME 和文件签名，并重新解码确认尺寸；不能只检查 API 是否存在。
- 浏览器不支持请求的导出格式时可能回退 PNG，必须核对结果，避免把 PNG 内容保存为 `.avif` 或 `.webp`。[MDN toBlob](https://developer.mozilla.org/en-US/docs/Web/API/HTMLCanvasElement/toBlob)
- 解码时统一 EXIF 方向，并用旋转、镜像样本检查；不要在浏览器已经应用方向后再次旋转。[MDN createImageBitmap](https://developer.mozilla.org/en-US/docs/Web/API/Window/createImageBitmap)
- 首版面向常规网页显示，采用 sRGB 工作目标；不保证跨浏览器逐像素相同，也不提供专业 ICC/CMYK、广色域和打印色彩工作流。
- 输出重新编码，不主动复制原文件 EXIF/GPS；在验收中检查输出元数据，不能把它宣传成未经验证的彻底匿名化工具。
- 有损编码不能保证文件一定变小；输出更大时如实显示。只有实际生成后才能显示最终字节大小。
- AVIF 在 V1.3 安排独立验证，必要时评估 `@jsquash/avif` 等浏览器 WASM 编码器，验证加载体积、编码耗时、内存和生产构建。jSquash 提供 AVIF 编解码包，但这不等于本项目已完成兼容验证。[jSquash 官方仓库](https://github.com/jamsinclair/jSquash)

V1.1 的文字水印还需等待字体就绪，并以同一字体资源进行预览与导出。使用系统字体时明确跨设备外观可能不同；如提供内置字体，应确认可分发并随站点托管。

## 7. 建议目录组织

以下是未来代码落点，不要求一次创建全部目录。先实现 V1.0 需要的模块，有第二个真实使用者时再抽取稳定共享能力。

```text
PicForge/
├── docs/
│   └── project-plan.md
├── public/
├── src/
│   ├── app/                 # 应用入口、页面组合、全局样式变量
│   ├── features/
│   │   └── stitch/          # 拼接工作台、参数、reducer、布局算法
│   ├── imaging/             # 图像领域：文件识别、解码、渲染、编码
│   ├── workers/             # 任务协议与 Worker 入口，调用 imaging
│   └── browser/             # 下载、能力检测、偏好存储等浏览器适配
├── tests/
│   ├── e2e/                # 真实浏览器流程
│   └── fixtures/           # 可公开使用的方向、透明、大图等样本
├── package.json
└── vite.config.ts
```

纯逻辑单元测试与被测模块邻近放置。后续在 `features/` 下分别增加 `watermark/`、`transform/`、`convert/`、`batch/`，仅在对应版本落实。

依赖方向：页面和任务入口调用图像能力；图像模块不依赖 React 或页面状态。Worker 协议只传任务描述、文件/可转移资源和结果，不引入 UI 类型。

手写生产源码文件优先控制在约 500 行以内，按职责拆分；避免把导入、布局、绘制、编码和表单全放进一个组件，也不建立职责不明的 `utils` 集合。

## 8. 隐私、存储与部署

### 8.1 隐私与本地状态

- 隐私承诺限定为：PicForge 不把用户选择的图片内容发送到服务端处理。
- 站点 HTML、JS、字体和 WASM 仍可能通过网络加载，不能把“本地处理”等同于“首次访问无需网络”。
- 默认不加入第三方分析或错误采集脚本；运行日志不记录图片内容、文件名或本地路径。
- localStorage 只保存布局偏好等小型配置；禁用存储或配额错误不能阻断工具使用。
- 原图和结果默认不持久化到 IndexedDB。若后续增加本地草稿，需要明确保存、清除、过期和容量行为。
- 首版仅接受本地文件，避免引入远程图片拉取、跨域画布污染和服务端代理。
- 用浏览器网络检查验证导入、编辑、导出过程没有携带图片数据的请求；允许正常静态资源加载。

### 8.2 部署形态

推荐交付 Vite 构建后的 `dist/`，托管到支持 HTTPS 的静态站点服务或现有 Nginx。若用户已有 Docker 管理习惯，可后续提供多阶段构建和静态服务容器。

运行环境只需提供静态资源，不需要常驻 Node 图片处理进程。运维成本主要是域名、静态存储和流量；不承诺任何平台永久免费。

部署验收包括：生产构建可访问、子路径资源正确、Worker/WASM 可加载、文件下载正常；增加 history 路由后配置入口回退，并确保不存在的静态资源仍返回正确错误。

HTML 使用可及时更新的缓存策略，带内容哈希的资源可长缓存。PWA/离线缓存作为后续增强，需要明确版本更新和缓存失效；首版不承诺离线刷新可用。

## 9. 开发阶段与工作量估算

以下按一名熟悉 React 的开发者估算有效工作日，用于安排顺序，包含开发与相应验证，不是交付承诺。复杂浏览器问题、设计返工和真实设备可用性可能增加耗时。

| 阶段                | 工作内容                                               | 产物及通过条件                                      | 估算   |
| ------------------- | ------------------------------------------------------ | --------------------------------------------------- | ------ |
| M0 技术验证         | 小图往返、EXIF 样本、Worker 降级、大图预算、手机保存   | 形成真实设备能力记录，确定输入/输出保护值与降级行为 | 2–3 天 |
| M1 工程与交互基础   | React/TS/Vite、类型检查、格式与 lint、工作台、导入列表 | 完成文件选择、错误反馈、排序及响应式基础            | 2–3 天 |
| M2 拼接引擎         | 三种布局、参数、预览、导出                             | 实际输出尺寸/顺序/透明度正确，预览和导出一致        | 4–6 天 |

V1.0 合计约 **11–17 个工作日**。先完成 M0 再细化时间与容量指标；移动端验证不足时应明确缩小支持范围，不能标记为已验证支持。

后续版本预估：V1.1 约 5–8 天，V1.2 约 5–8 天，V1.3 约 4–8 天，V2.0 约 7–12 天。AVIF 和大批量打包的不确定性较高，均需先做专项原型，再确认承诺范围。

V2.0 的流程模型建议采用“有序操作列表 + 独立输出任务”：先缩放/裁剪，再加水印，最后编码。模板保存参数和版本号，引用水印图片等素材时必须一并处理素材缺失；失败任务可单独重试。ZIP 的结果 Blob 也会占内存，必须限制累计结果大小或分包，不能因为任务逐张执行就假定整体内存有界。

## 10. 验证与验收标准

### 10.1 验证层次

- 纯逻辑：用 Vitest 测试布局、整数边界、参数校验、任务状态和过期结果处理。[Vitest 官方指南](https://vitest.dev/guide/)
- 浏览器集成：真实 Canvas 与编码 API 验证尺寸、MIME、透明度、方向和下载内容，不能只 mock Canvas 后宣布可用。
- 完整流程：Playwright 覆盖 Chromium、Firefox、WebKit，记录每次通过和失败的版本。[Playwright 浏览器文档](https://playwright.dev/docs/browsers)
- 真实设备：至少一台 iOS Safari 和一台 Android Chrome 验证大图、触控排序、取消和保存。Playwright WebKit/手机视口模拟不能替代真机结果。

### 10.2 V1.0 发布检查表

- [ ] 0 张、1 张、多张、混合横竖图、不同尺寸图片均得到明确结果。
- [ ] 横向、纵向、宫格的顺序、间距、外边距、末行规则与公式一致。
- [ ] PNG 透明通道正确，JPEG 背景正确，文件类型与后缀一致。
- [ ] 带 EXIF 旋转/镜像的图片不重复旋转，预览与导出方向一致。
- [ ] 文件损坏、格式不支持、解码失败、输出超限、编码返回空结果均可恢复。
- [ ] 连续调整参数时旧预览不覆盖新结果，取消导出后不会出现过期下载。
- [ ] 多轮导入、删除、清空、导出没有持续增长的资源滞留；记录测量环境。
- [ ] 360px、768px、1440px 视口可操作，键盘能走通主要流程。
- [ ] 浏览器网络检查未发现图片上传；原始本地文件没有被覆盖。
- [ ] 生产构建完成端到端验证；真实手机保存流程有明确记录。

### 10.3 首轮性能目标

以下是 M0 后需要校准的目标，不是当前已测结果：

- 对固定的 10 张 1920 × 1080 静态图片样本，在素材载入后，参数变更到预览更新的 P95 目标不超过 200ms。
- 导出不超过 1600 万像素的固定桌面样本，PNG/JPEG 完成时间目标不超过 5 秒；分格式记录，不能混算。
- 手机单独确定更保守的样本和预算；设备不满足预算时给出可操作提示。
- 性能报告记录设备、系统、浏览器、构建模式、图像样本、输出尺寸、格式和多次测量结果。

实现阶段按“相关单元测试 → 相关浏览器流程 → 完整构建与阶段验收”执行。每阶段在实际产生记录时补充进度文档，分清已实现、自动化验证、真机验证和未验证项。
